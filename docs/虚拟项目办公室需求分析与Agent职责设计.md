# 虚拟项目办公室需求分析与 Agent 职责设计

> [!summary]
> 本方案面向“项目 PMO / 周报 / 风险督办”的比赛场景，目标是构建一个运行在飞书多维表格 Base 上的“虚拟项目办公室”。它不是单点周报工具，而是一套由多个 Agent 扮演秘书、风控、追问、协调、汇报、复盘角色的组织运行系统。

## 1. 项目定位

### 1.1 场景定义

“虚拟项目办公室”是一个围绕项目过程数据运行的多 Agent 协同系统。

核心思路是：

- 项目成员持续在 Base 中更新项目、任务、里程碑、风险、会议纪要等数据
- Agent 不只是被动汇总，而是主动巡检、追问、识别风险、提出协调建议、生成周报与复盘
- 所有动作都通过真实的飞书多维表格 API / SDK / CLI 完成读写与回写

### 1.2 这个系统解决什么问题

真实项目管理中最常见的问题不是“没有表”，而是：

- 任务状态长期不更新
- 里程碑临期但没人主动预警
- 会议纪要有风险信号，但没有沉淀成可跟踪项
- 负责人过载，风险明明存在但没人统筹协调
- 每周花大量时间人工整理周报，且内容滞后
- 项目结束后很少系统性复盘，经验无法沉淀

本系统要解决的就是这些“项目办公室本该做、但人工做得很重”的工作。

### 1.3 项目定位一句话

> [!abstract]
> 这是一个“以 Base 为项目数据中枢，以 Agent 作为虚拟 PMO 员工”的项目治理系统。

### 1.4 非目标

为了防止方案过大，以下内容不作为本次比赛核心目标：

- 不做完整的研发流程平台替代 Jira、Tapd、禅道
- 不做复杂代码研发效能平台
- 不做全公司级权限治理系统
- 不做全开放式自然语言问答平台
- 不做高度自由的跨系统审批引擎

## 2. 业务目标与成功标准

### 2.1 业务目标

- 自动发现项目过程中的数据缺口与状态异常
- 自动识别延期、依赖、资源、需求变更等项目风险
- 自动向责任人发起追问并回收补充信息
- 基于负载和优先级提出资源协调建议
- 自动生成周报、风险摘要和管理层汇报
- 在项目结束后生成结构化复盘报告

### 2.2 成功标准

建议用下面几类指标作为验收指标：

- 任务更新及时率提升
- 超期未更新任务被识别率
- 高风险项目识别召回率
- 追问回复回收率
- 周报生成耗时下降
- 管理层查看项目状态的响应时效提升
- 项目复盘报告自动生成覆盖率

### 2.3 比赛视角下的亮点指标

- 每天自动巡检项目数
- 每周自动生成周报数
- 自动发现的高风险事项数
- Agent 通过 API 真实写回的记录数
- 自动追问闭环完成数

## 3. 参与角色

### 3.1 人类角色

- 项目成员：更新任务、回复追问、执行任务
- 项目负责人：确认优先级、处理风险、接收建议
- 管理层：查看周报、查看风险、做资源拍板
- PMO / 运营者：配置规则、观察系统运行、处理异常

### 3.2 Agent 角色

| Agent | 核心职责 | 主要输入 | 主要输出 |
|---|---|---|---|
| 项目秘书 Agent | 巡检任务、检查缺口、触发追问 | 项目表、任务表、里程碑表、会议纪要表 | 缺口清单、待追问事项、数据完整性结果 |
| 风险识别 Agent | 识别延期、依赖、资源、变更风险 | 任务表、里程碑表、风险问题表、会议纪要表 | 风险等级、风险原因、建议动作 |
| 追问 Agent | 向责任人发问并回写补充信息 | 缺口清单、风险待确认事项 | 追问消息、责任人回复、补充记录 |
| 资源协调 Agent | 提出资源调整、优先级重排、升级建议 | 项目优先级、负责人负载、风险列表 | 调整建议、协调方案、升级建议 |
| 周报 Agent | 汇总状态、生成周报、输出管理视角结论 | 项目表、任务表、风险表、会议纪要表 | 周报文档、风险摘要、管理层汇报 |
| 复盘 Agent | 统计延期原因、返工来源、需求变更与经验总结 | 项目历史数据、风险表、周报表、会议纪要表 | 复盘报告、经验建议、治理建议 |

### 3.3 一个关键理解

> [!important]
> 这 6 个 Agent 不是排队执行几个固定节点，而是围绕同一个项目问题分担“发现、判断、补信息、给方案、向上汇报、沉淀经验”这 6 个认知环节。

## 4.2 视图设计

- 表格视图：看全量明细
- 看板视图：看任务阶段、风险状态
- 甘特视图：看任务和里程碑排期
- 仪表盘：看延期率、风险数、负责人负载、里程碑完成率

## 4.3 共享数据中枢的意义

所有 Agent 协同的关键不是互相聊天，而是：

- 读取同一份业务真相
- 把自己的判断回写同一份业务系统
- 让下一个 Agent 在已有结果上继续工作

## 5. 核心协同闭环

## 5.1 标准业务闭环

`项目成员更新任务 -> 项目秘书检查缺口 -> 风险识别 Agent 判断风险 -> 追问 Agent 补齐信息 -> 风险识别 Agent 重新评估 -> 资源协调 Agent 生成方案 -> 周报 Agent 生成管理汇报 -> 管理层查看并拍板 -> 复盘 Agent 沉淀经验`

## 5.2 一次典型协同事件

以“里程碑 M3 可能延期”为例：

1. 项目秘书 Agent 发现关键任务长期未更新，且会议纪要中出现“接口变更”信号
2. 风险识别 Agent 初步判断为高风险，但信息不完整
3. 追问 Agent 向任务负责人和产品负责人发起追问
4. 责任人回复后，追问 Agent 把信息回写 Base
5. 风险识别 Agent 基于新信息重新评估，并确认延期概率高
6. 资源协调 Agent 输出资源调度建议和里程碑拆分建议
7. 周报 Agent 把该风险、原因和待拍板事项写入周报
8. 管理层据此做资源调配或节点调整
9. 复盘 Agent 在项目结束后分析这次延期的根因和改进建议

> [!tip]
> 这才是“协同”的完整含义：不是一条静态流程，而是多个角色围绕同一个问题逐步把异常变成信息，把信息变成判断，把判断变成行动。

## 6. 详细需求分析

## FR-01 多项目基础数据沉淀与状态建模

### 业务目标

统一沉淀项目、任务、里程碑、风险、纪要、周报数据，为所有 Agent 提供结构化事实基础。

### 业务痛点

- 项目数据分散在群聊、文档、口头同步里
- 没有统一状态字段，Agent 无法稳定判断
- 会议纪要与任务、风险脱节

### 功能要求

- 支持项目主数据录入与更新
- 支持任务、里程碑、风险、纪要、周报之间的关联
- 支持状态字段、负责人字段、时间字段结构化
- 支持 Agent 通过 OpenAPI 读写这些表

### Agent 在该需求中的动作

#### 项目秘书 Agent

- 检查表结构是否满足最小运行要求
- 检查关键字段是否为空
- 标记不可用记录

#### 风险识别 Agent

- 依赖这些结构化字段进行风险判断
- 对字段缺失的数据输出“无法可靠判断”的提示

#### 追问 Agent

- 对缺失负责人、缺失截止时间、缺失状态的记录发起补充追问

#### 资源协调 Agent

- 依赖项目优先级、负责人、任务工时等字段做后续协调

#### 周报 Agent

- 依赖统一结构化表生成稳定的摘要

#### 复盘 Agent

- 依赖历史过程数据做复盘

### 验收标准

- 6 张主表可用
- 表间关联清晰
- 关键字段完整率达到预设阈值
- Agent 可稳定读取与回写

## FR-02 任务巡检与数据缺口识别

### 业务目标

及时发现“数据没更新、状态不可信、纪要未同步、关键字段缺失”等问题。

### 业务痛点

- 项目看似正常，但真实状态没人维护
- 超期任务没有及时暴露
- 会议纪要提到的问题没有进入任务或风险系统

### 功能要求

- 定时巡检任务表和里程碑表
- 识别超期未更新任务
- 识别缺失负责人、缺失截止时间、缺失进度说明的记录
- 识别会议纪要是否未同步到任务/风险表

### Agent 在该需求中的动作

#### 项目秘书 Agent

- 作为该需求主责 Agent
- 每天定时扫描任务表和里程碑表
- 输出缺口清单
- 标记需要追问的事项

#### 风险识别 Agent

- 读取秘书 Agent 输出的缺口清单
- 判断这些缺口是否已上升为风险信号

#### 追问 Agent

- 对“长期未更新”“状态模糊”“缺字段”任务发起追问

#### 周报 Agent

- 在周报中汇总“数据治理问题”，例如长期未更新任务数

### 验收标准

- 可自动识别超期未更新任务
- 可输出缺口列表
- 可形成待追问记录

---

## FR-03 风险识别与分级

### 业务目标

让系统从“记录项目状态”升级到“主动识别项目风险”。

### 风险类型建议

- 延期风险
- 依赖阻塞风险
- 资源冲突风险
- 需求变更风险
- 沟通失真风险

### 功能要求

- 基于任务状态、截止时间、依赖链、会议纪要、负责人负载等数据综合判断风险
- 给出风险等级
- 说明触发原因
- 输出建议动作

### Agent 在该需求中的动作

#### 风险识别 Agent

- 作为该需求主责 Agent
- 读取任务、里程碑、纪要、风险历史记录
- 判断是否存在风险
- 输出风险类型、等级、原因、建议动作

#### 项目秘书 Agent

- 提供“异常数据入口”，如未更新、字段缺失、纪要未同步

#### 追问 Agent

- 当风险判断缺少证据时，负责补齐信息

#### 资源协调 Agent

- 对高风险项目生成资源与优先级调整建议

#### 周报 Agent

- 把高风险事项写入本周管理摘要

### 验收标准

- 风险识别结果能回写风险问题表
- 每个风险项都带原因说明
- 高风险项都能产生建议动作

---

## FR-04 自动追问与信息补全

### 业务目标

对“状态不清楚、风险未确认、字段缺失、任务长期未更新”的事项自动发起追问，并将回复沉淀回 Base。

### 业务痛点

- 数据不完整时，系统只能停在“怀疑有风险”
- 人工追问成本高且容易漏
- 管理动作没有沉淀回表

### 功能要求

- 能根据缺口清单自动生成追问内容
- 能定向找到责任人
- 能记录追问时间、追问对象、追问内容、回复结果
- 能把补充信息回写表格

### Agent 在该需求中的动作

#### 追问 Agent

- 作为该需求主责 Agent
- 根据秘书 Agent 和风险 Agent 输出的问题生成有针对性的追问
- 发送飞书消息或其他指定渠道
- 记录追问状态与回复结果
- 回写任务说明、阻塞原因、确认时间等字段

#### 项目秘书 Agent

- 提供待追问列表

#### 风险识别 Agent

- 明确“缺的是什么证据”

#### 周报 Agent

- 汇总未回复的追问项和已闭环项

### 验收标准

- 追问信息不是固定模板，而是基于缺口上下文生成
- 回复结果能回写 Base
- 可统计追问回复率和闭环率

---

## FR-05 风险处置与资源协调建议

### 业务目标

系统不能只发现问题，还要提出可执行的解决方案。

### 业务痛点

- 风险暴露后没人快速做资源统筹
- 任务优先级不清，所有项目都喊急
- 负责人负载不均衡

### 功能要求

- 根据风险等级、项目优先级、人员负载、依赖关系提出建议
- 支持输出调整建议、替换建议、升级建议、里程碑调整建议

### Agent 在该需求中的动作

#### 资源协调 Agent

- 作为该需求主责 Agent
- 读取项目优先级、负责人负载、关键路径风险
- 输出资源调配建议
- 输出优先级重排建议
- 输出需要管理层拍板的事项

#### 风险识别 Agent

- 提供风险等级和触发原因

#### 项目秘书 Agent

- 提供过期任务、里程碑临期、缺口状态

#### 周报 Agent

- 把建议动作升级为管理决策项

### 验收标准

- 每个高风险事项至少可生成一种处置建议
- 建议可回写风险表或周报表
- 可区分“系统建议”和“待人工拍板”事项

---

## FR-06 周报、风险摘要与管理汇报生成

### 业务目标

基于项目真实运行数据自动生成管理层可读的汇报材料。

### 业务痛点

- 周报高度依赖人工手写
- 汇报内容滞后且口径不一致
- 风险没有沉淀为可决策信息

### 功能要求

- 自动生成项目周报
- 自动生成风险摘要
- 自动生成下周计划
- 自动写入飞书文档并回写链接到周报表

### Agent 在该需求中的动作

#### 周报 Agent

- 作为该需求主责 Agent
- 汇总项目状态、关键任务、风险、阻塞项、下周计划
- 输出管理层视角摘要
- 输出需要领导拍板事项
- 创建文档并回写链接

#### 项目秘书 Agent

- 提供本周数据完整性结果

#### 风险识别 Agent

- 提供高风险列表和风险原因

#### 资源协调 Agent

- 提供资源调整建议和升级建议

### 验收标准

- 周报内容来源于 Base 真实数据
- 周报中包含进展、风险、阻塞、建议
- 文档链接成功回写

---

## FR-07 管理层查询与项目驾驶舱

### 业务目标

让管理层能快速获取“哪个项目最危险、哪些任务最滞后、哪些负责人过载”等信息。

### 说明

这个需求建议做成 MVP 可选增强项，不必一开始就做完全开放式问答。

### 功能要求

- 支持固定问题模板查询
- 支持基于仪表盘和周报表回答管理问题
- 支持输出 Top 风险项目、Top 延期任务、Top 过载负责人

### Agent 在该需求中的动作

#### 周报 Agent

- 兼任管理查询的摘要生成入口
- 基于结构化数据与已生成周报回答问题

#### 项目秘书 Agent

- 提供实时项目状态索引

#### 风险识别 Agent

- 提供当前高风险项目排序

### 验收标准

- 可回答 3 到 5 个固定管理问题
- 回答内容来源于 Base 和周报表

---

## FR-08 项目复盘与经验沉淀

### 业务目标

让项目结束后能系统性地总结延期、变更、返工、沟通失真等问题，并沉淀经验。

### 业务痛点

- 项目结束后复盘靠人回忆，主观性强
- 历史问题无法转化为组织经验

### 功能要求

- 统计延期原因
- 统计需求变更次数
- 分析返工来源
- 总结风险识别滞后点
- 输出改进建议

### Agent 在该需求中的动作

#### 复盘 Agent

- 作为该需求主责 Agent
- 读取项目全生命周期数据
- 统计异常项、风险项、变更项、追问项
- 输出项目复盘报告
- 输出下一次项目治理建议

#### 周报 Agent

- 提供历史周报作为阶段性证据

#### 风险识别 Agent

- 提供历史风险记录作为复盘输入

#### 项目秘书 Agent

- 提供历史缺口与数据质量问题记录

### 验收标准

- 项目结束后可自动生成复盘报告
- 复盘报告能说明问题来源、影响、建议

---

## FR-09 可追溯、可解释与行为审计

### 业务目标

比赛和实际系统都需要保证“每个 Agent 做过什么、为什么这么做、写了什么结果”可追踪。

### 功能要求

- 记录每次 Agent 触发时间
- 记录输入来源表和记录 ID
- 记录输出结果和回写字段
- 记录风险判断原因或摘要

### Agent 在该需求中的动作

#### 所有 Agent

- 每次执行都必须留下运行记录
- 记录读了哪些表、更新了哪些字段
- 记录异常与失败原因

#### 周报 Agent

- 在文档中引用关键数据来源

#### 风险识别 Agent

- 输出可解释的风险原因

### 验收标准

- 不依赖口头解释即可回放 Agent 行为
- 能证明系统是真实调用而非 mock

---

## FR-10 持续运行与触发机制

### 业务目标

系统不是只演示一次，而是能持续运行并持续产出数据和报告。

### 触发方式建议

- 定时巡检触发
- 新任务 / 新纪要写入触发
- 风险升级触发
- 周报周期触发
- 项目结束触发复盘

### Agent 在该需求中的动作

#### 项目秘书 Agent

- 每日巡检触发

#### 风险识别 Agent

- 巡检后或新增风险信号后触发

#### 追问 Agent

- 秘书或风险识别结果产生待补信息时触发

#### 周报 Agent

- 每周固定时间触发

#### 复盘 Agent

- 项目状态变为“已完成”后触发

### 验收标准

- 系统支持日常自动运行
- 能产生持续积累的数据与文档

## 8. MVP 建议

## 8.1 建议的最小可行版本

如果比赛时间有限，建议优先做下面 5 个核心能力：

- FR-01 数据沉淀与建模
- FR-02 任务巡检与缺口识别
- FR-03 风险识别与分级
- FR-04 自动追问与信息补全
- FR-06 周报与汇报生成

## 8.2 MVP 中 Agent 建议保留

- 项目秘书 Agent
- 风险识别 Agent
- 追问 Agent
- 周报 Agent

## 8.3 第二阶段增强能力

- 资源协调 Agent
- 复盘 Agent
- 管理层问答

## 8.4 为什么这样拆

这样做的好处是：

- 先把“发现问题 -> 补充信息 -> 生成汇报”的闭环跑通
- 保证 Base 真实读写先稳定
- 再补“协调”和“复盘”这两个更偏高阶认知的能力

---

## 9. 风险与边界

### 9.1 主要风险

- 原始数据质量差，导致 Agent 判断失真
- 风险识别过于规则化，显得像普通 workflow
- 周报生成只像“自动写作文”，缺少决策含量
- 追问消息泛滥，影响用户体验
- 资源协调建议缺少真实组织约束，显得空泛

### 9.2 应对策略

- 明确关键字段的最小必填要求
- 风险识别结合多源数据，而不是只看一个状态字段
- 周报必须包含风险、阻塞、建议和待拍板事项
- 追问增加节流规则与优先级
- 资源协调先做“建议”，不直接自动改动责任人

### 9.3 一句总结

> [!important]
> 这个系统的价值不在于“帮人自动写一份周报”，而在于“像一个虚拟 PMO 办公室一样，持续发现问题、补齐信息、识别风险、提出动作并沉淀经验”。

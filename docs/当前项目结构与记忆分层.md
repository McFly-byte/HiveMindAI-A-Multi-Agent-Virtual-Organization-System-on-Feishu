# 当前项目结构与记忆分层

本文用于合并分支后的结构对齐。核心原则：**`src/` 里的代码才是正式运行时和真正的 agent loop**；根目录下的 `agents/`、`projects/` 是运行时配置与项目工作区；`pmo_mvp/` 是旧 MVP/demo 代码，后续不应继续承载正式 runtime 能力。

## 结论先行

| 结论 | 说明 |
| --- | --- |
| 正式 agent loop 在 `src/agent_runtime/` | `AgentRuntime.run_agent()` 创建并驱动 `src/agent_runtime/session.AgentSession`。 |
| 正式工具执行在 `src/tool_integration/` | `ToolIntegrationExecutor.call_tool()` 负责权限校验、调用工具、把工具调用写入 `session.steps`。 |
| 飞书 API 封装在 `src/feishu_adapter/` | 业务 Agent 不应直接依赖飞书 SDK；应通过 tool integration 调用注册工具。 |
| Agent 配置与 prompt 在 `agents/*` | `agent.yaml` 是权限、模型、runtime limits 等配置；`AGENT.md` 是 agent 点记忆/系统提示词。 |
| 项目配置与项目点记忆在 `projects/*` | `PROJECT.md`、`project_state.yaml`、`table_manifest.yaml` 是项目运行上下文。 |
| `pmo_mvp/` 是旧 demo 层 | `run_demo.py`、`pmo_mvp/agents.py`、`pmo_mvp/memory` 不在 `pyproject` 的正式包发现路径内。 |
| 记忆系统需要迁入 `src/` 才能接入真实 loop | 当前 `pmo_mvp/memory` 的 SQLite store/toolset 是 prototype，不能直接作为正式 runtime 归属。 |

## 当前目录职责

```text
.
├── src/
│   ├── agent_runtime/        # 正式 agent loop、session、事件、配置、质量门、MVP handler
│   ├── tool_integration/     # 工具注册、schema 校验、执行器、事件总线、后台 job
│   └── feishu_adapter/       # 飞书 API 工具封装
├── agents/                   # Agent 工作区：AGENT.md + agent.yaml
├── projects/                 # 项目工作区：PROJECT.md + project/table manifest
├── tool_integrations/        # 仓库级扩展工具，如 trace_tool
├── scripts/                  # 正式 demo/运行脚本，当前主要是 run_mvp_demo_chain.py
├── traces/                   # LocalJsonlTraceSink 输出
├── tests/                    # 以 src 为主的测试；conftest.py 会把 src 加入 sys.path
├── pmo_mvp/                  # 历史本地 JSON demo，不是正式 runtime
├── run_demo.py               # 历史 demo CLI，仍依赖 pmo_mvp
└── runtime/ output/ uploads/ # 历史 demo 或本地运行产物
```

## 正式运行链路

当前真实链路从 `scripts/run_mvp_demo_chain.py` 进入：

```text
scripts/run_mvp_demo_chain.py
  └─ build_runtime_with_tool_integration()
       ├─ load_runtime_config(root)
       │    └─ load agents/*/agent.yaml
       ├─ build_tool_integration_executor()
       │    ├─ scan src/feishu_adapter
       │    └─ scan tool_integrations
       ├─ MVPAgentRegistry
       ├─ SimpleRuleQualityGate
       └─ LocalJsonlTraceSink

AgentRuntime.run_agent(request)
  ├─ create_session(event, agent_name)
  │    └─ returns src.agent_runtime.session.AgentSession
  ├─ trace_sink.on_session_start(session)
  ├─ handler.run(session, payload)
  │    ├─ tool_executor.call_tool(..., session)
  │    │    └─ append ToolCallRecord into session.steps
  │    └─ returns AgentOutput / CoordinatorPlan
  ├─ append output into session.memory as SessionMemoryItem
  ├─ session.mark_success() / mark_failed()
  └─ trace_sink.on_session_end(session)
```

### 当前正式 `AgentSession`

正式 `AgentSession` 位于 `src/agent_runtime/session.py`。它是**agent loop 的运行态短期记忆对象**，不是 `pmo_mvp/memory` 里的 SQLite session。

它现在包含：

- run identity：`session_id`、`run_id`、`parent_run_id`、`trace_id`
- scope：`project_id`、`agent_name`、`trigger_type`、`trigger_user`
- lifecycle：`status`、`started_at`、`ended_at`、`retry_count`
- loop trace：`current_step_index`、`max_steps`、`steps`
- IO trace：`input_record_ids`、`output_records`、`read_sets`、`write_sets`
- short-lived memory：`memory: list[SessionMemoryItem]`
- error and final output：`errors`、`final_output_ref`、`final_summary`

`ToolIntegrationExecutor` 会在工具调用时把 `ToolCallRecord` 写入 `session.steps`；`AgentRuntime` 会在 handler 返回 Pydantic output 时把结果写入 `session.memory`。

## 容易混淆的概念

| 概念 | 当前正式位置 | 是否属于正式 loop | 说明 |
| --- | --- | --- | --- |
| `AgentSession` | `src/agent_runtime/session.py` | 是 | run 内热状态和短期记忆，handler/tool executor 直接修改它。 |
| `SessionMemoryItem` | `src/agent_runtime/session.py` | 是 | 当前 run 内输出和临时记忆，主要用于链式传递。 |
| `AgentContext` | 当前 `src` 里尚未抽象成独立对象 | 应该属于 runtime/context 层 | 未来用于承载 session、context manager、memory adapters 等运行上下文入口。 |
| `pmo_mvp.memory.AgentSession` | `pmo_mvp/memory/store.py` | 否 | 旧 prototype 里的 SQLite 持久化 session，名称与正式 `AgentSession` 冲突。 |
| `pmo_mvp.memory.MemoryStore` | `pmo_mvp/memory/store.py` | 否 | 目前不在正式包 `src` 内，不能作为正式 runtime 直接依赖。 |
| `AgentRunRecord` | `src/agent_runtime/agent_runs.py` | 是 | 从 `AgentSession` 派生的可序列化 AgentRuns 表行。 |
| `ProcessEvent` | 目前只有 `pmo_mvp/memory` prototype | 否 | 正式 runtime 目前用 trace sink 和 session.steps 承担过程记录。 |

## 记忆分层应该怎么放

推荐把记忆能力按以下边界迁入 `src`，而不是继续放在 `pmo_mvp/`：

| 层级 | 正式归属建议 | 说明 |
| --- | --- | --- |
| 点记忆 | `agents/*/AGENT.md`、`projects/*/PROJECT.md`，由 `agent_runtime.loaders` 读取 | 已经基本成型。不要再另建 `runtime/memory/agents/*/AGENT.md` 作为正式来源。 |
| 短期记忆 | `src/agent_runtime/session.py` | 当前 `AgentSession.memory`、`steps`、`errors` 就是 run 内短期记忆基础。 |
| 上下文管理/compact | 新增 `src/agent_runtime/context.py` 或 `src/agent_runtime/context_manager.py` | 负责 messages/tool results/scratchpad 裁剪、compact summary、checkpoint 策略。 |
| 过程记忆 | 先复用 `session.steps` + `LocalJsonlTraceSink`，后续可新增 `src/agent_runtime/process_log.py` | `process_events` prototype 可以迁入，但不要和 loop session 混名。 |
| 长期记忆 | 新增 `src/agent_runtime/memory/` 或 `src/memory_runtime/` | 迁移 SQLite/FTS/vector store；对外提供 adapter，不直接污染 handler。 |
| 记忆 tools | 注册到 `src/tool_integration` 体系 | LLM/Agent 调记忆也应走 tool registry、权限和审计，不应绕过 `ToolIntegrationExecutor`。 |

## 命名调整建议

为避免两个 `AgentSession` 混淆，迁移 memory prototype 时建议改名：

| 旧名 | 建议新名 | 原因 |
| --- | --- | --- |
| `pmo_mvp.memory.AgentSession` | `PersistedSessionCheckpoint` 或 `AgentSessionCheckpoint` | 它是 SQLite 持久化快照，不是 runtime session 本体。 |
| `pmo_mvp.memory.ProcessEvent` | `ProcessLogRecord` | 与 tool integration event / trigger event 区分。 |
| `MemoryToolset` | `MemoryToolProvider` 或 `MemoryToolRegistrar` | 正式接入时应注册为 `tool_integration` tools。 |
| `MemoryStore` | 可保留，但应迁到 `src/agent_runtime/memory/store.py` | 作为底层存储 adapter。 |

## 迁移路线

### 第一步：停止扩展旧 demo 入口

- 新 agent loop、session、context、tool 能力只放 `src/`。
- `pmo_mvp/` 和 `run_demo.py` 保留为历史本地 JSON demo，除非明确做兼容修复，否则不再新增正式能力。
- 根 README 应改成指向 `scripts/run_mvp_demo_chain.py` 和 `docs/开发指引.md`，而不是只描述旧 `pmo_mvp`。

### 第二步：把 memory prototype 迁到正式 runtime

建议目标目录：

```text
src/agent_runtime/memory/
├── __init__.py
├── store.py          # SQLite/FTS/vector backend
├── retrieval.py
├── embedding.py
├── doc_pipeline.py
├── checkpoints.py    # AgentSession checkpoint / compact summary 持久化
└── tools.py          # 注册 memory tools 到 ToolRegistry
```

迁移时需要做的语义调整：

- 不再定义另一个 `AgentSession`。
- SQLite 的 session 表只保存 `run_id` 对应 checkpoint/summary，不拥有 runtime session 生命周期。
- `src/agent_runtime/session.AgentSession` 仍是 handler 和 tool executor 的唯一 session 对象。
- compact summary 由 runtime/context manager 生成，memory store 只保存。

### 第三步：新增 runtime context 管理层

建议新增：

```text
src/agent_runtime/context.py
```

职责：

- 构建 handler/LLM prompt 所需上下文。
- 管理 run 内 hot memory：messages、tool results、scratchpad、retrieved memories。
- 判断是否 compact。
- 生成 compact summary。
- 把 checkpoint 写入 memory store。
- 从长期记忆检索相关 context。

注意：`AgentContext` 是运行时依赖入口，不是短期记忆本体；短期记忆本体仍是
`AgentSession` 和它持有的 hot state/checkpoints。

### 第四步：把 memory tools 纳入 tool policy

正式 memory tools 应像飞书 tools 一样被注册：

- `memory_search`
- `memory_write`
- `memory_reflect`
- `session_checkpoint`
- `project_context_get`
- `doc_search`

然后在 `agents/*/agent.yaml` 的 `tool_policy.allowed_tools` 中按需开放。这样记忆访问也能被 `ToolIntegrationExecutor` 审计到 `session.steps`。

## 当前优先级建议

1. **先改文档入口**：根 `README.md` 仍是旧 `pmo_mvp` 说明，容易误导。应改为当前 `src` 架构。
2. **统一 AgentSession 语义**：正式 `AgentSession` 只保留 `src/agent_runtime/session.py` 这一份。
3. **迁移 memory 到 `src`**：不要让正式 runtime 依赖 `pmo_mvp.memory`。
4. **补 context manager**：把 compact summary、上下文裁剪、checkpoint 放在 runtime context 层。
5. **把 memory tools 注册到 tool integration**：保证 tool policy、trace、审计统一。
